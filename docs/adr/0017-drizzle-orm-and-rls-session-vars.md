# ADR-0017: Drizzle ORM with Postgres RLS via session variables

- **Status**: Accepted
- **Date**: 2026-05-10
- **Deciders**: AuditForge core
- **Phase**: 7 (data layer) → 7.5 (memory layer)
- **Tags**: database, orm, security, rls, multi-tenancy

## Context

`CLAUDE.md` mandates Drizzle as the ORM and Postgres RLS for tenant
isolation ("defense in depth + app guards"). Wave-1 wired real Drizzle
handlers across `packages/db`, `packages/audit-engine`, `packages/findings`,
`packages/working-papers`, and the API repositories. Two questions had to be
answered before writing those handlers:

1. Schema-first vs migration-first authoring? Drizzle supports both, but
   review velocity and AI codegen both prefer types derived from the schema.
2. How does an application-layer transaction propagate the auditor's identity
   to the Postgres RLS policies? Connection pooling rules out per-tenant
   roles; embedding `WHERE tenant_id = $1` in every handler is exactly the
   "app guard only" approach `CLAUDE.md` rules out.

## Decision

Adopt Drizzle in **schema-first** mode (the source of truth lives under
`packages/db/src/schema/*.ts`; migrations are generated by `drizzle-kit`)
and propagate auditor identity to RLS using **session variables** set
inside every transaction:

```ts
await db.transaction(async (tx) => {
  await tx.execute(sql`SELECT set_config('app.user_id', ${userId}, true)`);
  await tx.execute(sql`SELECT set_config('app.firm_id', ${firmId}, true)`);
  // ... handler body uses tx ...
});
```

`set_config(name, value, is_local=true)` scopes the variable to the current
transaction so a connection returning to the pgbouncer pool carries no
auditor context. RLS policies reference `current_setting('app.user_id')`
and `current_setting('app.firm_id')` to filter every row read or write.

The pattern is encoded once in `packages/db/src/with-rls.ts` and applied by
every repository (`@auditforge/findings`, `@auditforge/working-papers`,
`@auditforge/engagement`, etc.) via a small wrapper: handlers never call
`db.transaction` directly, they call `withRls(principal, fn)`.

## Consequences

### Positive

- **Defense in depth**: a missing app-side filter does not leak data — the
  RLS policy still drops rows whose `firm_id` does not match the session
  variable.
- **Type safety**: schema-derived types flow to all consumers; the
  `repository → handler → API → web` chain shares one source of truth.
- **Pooler-compatible**: `is_local=true` means pgbouncer transaction pooling
  works; we do not need a connection-per-tenant.
- **Auditable**: RLS policies are reviewable artefacts (under
  `packages/db/migrations/*_rls.sql`); per-PR security review covers them.

### Negative

- **Repository discipline required**: forgetting `withRls()` in a new
  handler is a silent bug (data is still readable for the test user). We
  mitigate with a Semgrep rule (`semgrep/free-form-llm-output.yml` style)
  and with integration tests that run as a non-superuser DB role.
- **Triggers must SET LOCAL too**: any DB function that re-enters a
  transaction-bound code path needs `SECURITY INVOKER` or it will not
  observe the session variables; this caught us once and is documented in
  `packages/db/README.md`.

### Neutral

- We chose Drizzle over Prisma to keep the dependency surface small (Prisma
  ships a Rust query engine; Drizzle is pure TypeScript) and because
  Drizzle's SQL builder makes RLS policies trivial to express alongside
  the schema.

## Alternatives Considered

| Option | Why rejected |
|--------|--------------|
| Per-tenant Postgres roles | Doesn't scale beyond a few hundred tenants; pgbouncer transaction pooling becomes useless. |
| App-level filtering only | Violates `CLAUDE.md` "Postgres RLS for tenant isolation". |
| Schema-less or string-SQL ORM | Loses TypeScript type safety; AI codegen produces too many runtime errors. |
| `SET ROLE` per request | Requires SUPERUSER to switch back; unsafe in connection pool. |

## Compliance Implications

- **ISO 42001 Clause 8.2** (operational planning and control): tenant
  isolation is an operational control; RLS policies are documented and
  testable.
- **ISO 17021-1 Clause 8.5** (impartiality and confidentiality of audit
  records): cross-tenant leakage is structurally prevented.
- **EU AI Act Art. 10** (data governance): bi-temporal claim graph
  (ADR-0009) inherits the same RLS pattern.
