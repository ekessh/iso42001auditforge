# Reports and Signing

> This document covers report generation, the Ed25519 + RFC 3161 signing
> pipeline, and how the audit ledger anchors the issued report.

---

## Report Types

| Type | When generated | Format |
|---|---|---|
| Audit Report (Stage 1) | After Stage 1 engagement | DOCX + PDF/A-3 |
| Audit Report (Stage 2) | After Stage 2 engagement | DOCX + PDF/A-3 |
| Surveillance Report | After surveillance engagement | DOCX + PDF/A-3 |
| Re-certification Report | After re-certification | DOCX + PDF/A-3 |
| Readiness Report | After Readiness Mode engagement | DOCX + PDF/A-3 (with mandatory disclaimer) |

All reports are generated by `packages/report-engine`.

---

## Generating a Report

1. From the engagement, click **Generate Report**
   (`POST /v1/reports`).
2. Select the report type and template.
3. The system pre-fills:
   - Engagement metadata (client, dates, scope, team).
   - Coverage summary (clause-by-clause status).
   - All formal findings (major NCs, minor NCs, OFIs).
   - CAPA status for each finding.
   - Evidence annex (linked evidence files with chain-of-custody).
   - Probe results summary.
   - Sampling records.
4. The lead auditor writes the **Conclusion** section directly in the
   report editor. The engine does not write the conclusion.
5. Click **Save Draft**.

---

## PDF Rendering

Click **Render PDF** (`POST /v1/reports/{id}/render`). The worker:

1. Converts the DOCX template + data to a PDF using LibreOffice.
2. Validates the PDF for PDF/A-3 compliance using VeraPDF.
3. Embeds evidence attachments as PDF/A-3 attachment streams.
4. Returns the rendered PDF (available at `GET /v1/reports/{id}`).

If PDF/A-3 validation fails, the render job returns an error with the
specific compliance failure. The operator guide covers PDF/A configuration
at [../operator-guide/10-upgrades.md](../operator-guide/10-upgrades.md).

## Signing Pipeline

When the lead auditor is satisfied with the report:

1. Click **Sign and Issue** (`POST /v1/reports/{id}/sign`).
2. The system:

   a. Computes the **JCS canonical JSON** of the report payload.

   b. Signs with the auditor's **Ed25519 key**. In production, the key
      is stored in the HSM/KMS. In development, `SoftwareSigningProvider`
      is used (never in production).

   c. Requests an **RFC 3161 timestamp token** from the configured TSA
      (default: FreeTSA; configurable per firm). The TSA token is
      attached to the report payload.

   d. Writes a `report.publish` event to the audit ledger. This event
      carries the report hash, the Ed25519 signature, and the TSA token.
      It is itself signed and chained to the prior ledger event.

   e. The engagement transitions to `issued`.

3. The signed report is available for download as DOCX and PDF/A-3.

---

## Verification

Anyone with the issued report and the firm's public key can verify:

1. The Ed25519 signature over the report canonical hash.
2. The TSA token (using the TSA's public certificate, publicly available).
3. The audit ledger chain up to and including the `report.publish` event.

`POST /v1/admin/chain/verify-all` runs the full chain verifier. See
[../concepts/signing-and-tsa.md](../concepts/signing-and-tsa.md) for the
cryptographic walkthrough.

---

## Long-Term Archival

For reports requiring long-term archival (10+ years):

1. The TSA token is renewed annually by the `tsa-renewal` worker job.
2. CAdES-LT / PAdES-LTV is applied using additional TSA providers for
   multi-layer validation.
3. The operator configures the archival chain in the Helm values; see
   [../operator-guide/06-backup-and-restore.md](../operator-guide/06-backup-and-restore.md).
